# To Fix

Open bugs in the Inform app and in Zoom and CocoaGlk, found during the modernisation (`modernisation_plan.md`). When one is fixed, take it out of here and record the fix in the plan, with the work it was fixed in. Problems that belong in Inform Core itself are in `for_g.txt`, a local, git-ignored list.

Each says how it was found, and none has been seen in the app unless it says so.

## Running Inform's tools

- **Some run-time problems are never shown.** When turning a run-time problem's Markdown into a page fails, `IFProjectController`'s `runtimeError:inDirectory:` returns without showing anything, so neither the problem nor the error page that `IFInBuild` writes is seen. Found by reading (6 November 2026).
- **A run-time problem the app has no page for shows a missing page.** For a problem the story names no folder for (a numbered problem from an older story, or a named one in a story compiled without debugging), `IFRuntimeProblemPage` gives the app's `RTP_` page for it, or failing that `RTP_Unknown.html`, but there has never been such a page in the app. Found by reading (9 November 2026); not checked in the app.
- **Every project's Errors page shows every project's intest runs.** `IFCompilerController` observes InTest's notifications from any object, so with two projects open, each console shows the other's runs too, such as the catalogue made whenever an extension project is opened or saved. Found by reading (6 November 2026).
- **A tool that wrote a lot of errors would hang the app.** `IFInBuild` and `IFInTest` only read a tool's stderr once its stdout has ended, so if it wrote more to stderr than a pipe holds (64 KB), each would wait for the other. inbuild and intest write a line or two there. Found by reading (6 November 2026).
- **A missing tool raises an exception.** If `inbuild` or `intest` can't be found, which can only happen with an external Inform Core folder (Advanced preferences), launching it raises. `IFMaintenanceTask` raises the same way for a command it can't run, and its queue is then stuck, though the only command it's given is the app's own 6M62 `ni`. Found by reading (6 November 2026).
- **Go runs the old story after an extension the project includes is changed.** `IFCompileCheck` skips the compile when the project has no unsaved changes and its story is newer than its own source and settings, so after an installed extension, or one in the project's materials folder, is edited and saved, Go, Replay and Play All say "No compilation required." and run the story made with the old extension. Release, Test Me and Refresh Index always compile. Mending it means choosing how far to look, such as at the extensions folders' modification times, or compiling every time, as the Advanced preferences' Always Compile does. Found by reading (9 November 2026); not checked in the app.
- **The `build.sh` stage can be left queued.** With "Rebuild I7 compiler as needed" chosen in the Advanced preferences (for maintainers of Inform), `IFCompiler`'s `prepareForLaunchWithBlorbStage:testCase:` queues `~/build.sh` before checking that there's an Inform 7, and when there isn't (only possible with an external Inform Core folder), it returns NO with that stage still queued, so the next build runs only `build.sh`. Found by reading (6 November 2026).
- Harmless as the app uses it: `IFMaintenanceTask` only posts the last task's notification, when the queue empties, so a task queued behind another never posts its own. Every run of censuses ends with `IFCensusFinished`, which everything that observes the other census notification observes too. A test pins it.

## Extension projects

- **The Public Library page and the app disagree about their messages.** `messages_to_objc.js` posts `askInterfaceForLocalVersion`, `askInterfaceForLocalVersionText` and `downloadMultipleExtensions`, which `IFWebViewHelper` doesn't act on, and its `openURL` posts `openFile`, so the helper takes the URL for a file's path. Inform Core's `pl404.html` also uses the first two's return values at once, which WKWebView messages can't give, so this needs an asynchronous design on both sides (see `for_g.txt`). The helper had handlers for the first two under other names, which nothing reached and whose answers were thrown away; they were taken out (a84b8641), and the lookup of an installed extension's version will have to be written for that design. Older than this work; found reading the scripts (November 2026).
- **An extension project's skeins can be passed over, or left over.** `IFProjectFile` finds each of `SkeinA.skein`, `SkeinB.skein` and so on by comparing file names without regard to case, but then reads it by its exact name, so one named in other case, such as `skeina.skein`, is passed over, with every letter after it. And writing fewer skeins than there are files leaves the later files in the project, to be read again when it's next opened; what `IFProject` then does with the extra skein isn't checked. Neither is likely. Found with the `IFProjectFile` tests (6 November 2026).

## Projects

- **Revert To Saved doesn't revert a project.** The File menu's Revert To Saved reads the project again, which gives `IFProject` new texts for its source files, but the source page keeps showing, and editing, the old ones, so edits made after reverting aren't saved. And reading the skeins again adds them to the ones the project has (`IFProjectFile`'s `loadIntoSkeins:` doesn't empty the list first), so the project goes on showing its old skein. Found by reading (6 November 2026). Reading the project again also gives it new settings, but the Settings tab keeps showing, and changing, the old ones, which are neither saved nor used to compile. Found by reading (8 November 2026).
- **Retrying a failed Save Compiler Output loses its window.** `IFProject`'s `saveCompilerOutputWithWindow:` forgets its window as soon as the save panel is shown, so when the copy fails and Retry is chosen, it's tried again with no window: the save panel is begun as a sheet on no window (which, for `IFUtility`'s alerts, showed nothing at all), and the Swift method, which declares its window non-null, is given nil. Found by reading (6 November 2026).
- **Saving the iFiction record, or exporting an extension, over an existing file does nothing.** The save panel asks whether to replace the file, but the copy fails when the file is there, and the failure isn't reported, so the old file stays. Save Compiler Output removes the old file first. Found by reading (6 November 2026).
- **A new story's opening line can be one Inform rejects.** `IFNewInform7Project` writes `"<project name>" by <author>` as a new story's first line, putting the author's name in quotation marks only when it has a full stop. Inform 7 v10.2.0 rejects the line when the project's name has a `"` in it ("The opening bibliographic sentence can only be a title in double-quotes") or a `[` (taken as a text substitution), and when the author's name, from the preferences or the user's name, has a `"` or a `;` in it, so a project made with such a name won't compile until its first line is edited. Mending it means choosing what to put in their place, such as `'` for `"` (which Inform prints as a double quote) and quoting more authors' names. Checked with the app's `ni` (7 November 2026).
- **A new extension's opening line can be one Inform rejects.** The New Extension window (`IFNewInform7ExtensionFile`) suggests the author's name from the preferences, in quotation marks when it has a full stop, as for a story, and writes `<title> by <author> begins here.` as the extension's first line, in a folder named for the author, quotation marks and all. Inform 7 v10.2.0 finds the extension there, but rejects it, as its opening line has a `"`. Without them, the extension's own line is accepted, but an `Include` of it ends at the author's first full stop, so Inform can't find the extension; and an `Include` with them looks in the folder with them. So an author's name with a full stop can't be used for an extension at all, and a title or author with a `"` typed in is rejected too. Mending it means choosing what to do with such names, such as leaving the full stops out or refusing them in the window. Checked with the app's `ni` (7 November 2026).
- **An alert that a new project or extension couldn't be written may never be seen.** When a new project or extension can't be written, `IFNewProject` begins a sheet saying so on the New Project window, and then closes the window. For New Extension the window is open when the sheet begins; for New Project and New Extension Project it was never shown. Either way the sheet probably goes with the window. Found by reading (8 November 2026).
- **The toolbar's status never shows a message.** `IFToolbarStatusView` shows messages, such as "No compilation required." and the compiler's stages, in a title above the story line and the progress bar, and hides the title when there's no room for it. The toolbar manager makes the view 30 points high, where there never is (it would need about 38), so messages are never seen. If the title had room, `showMessage:` would also need to hide the welcome, which it leaves to the view's next change of what it shows. Mending it means choosing where messages go, such as in place of the story line. Found with the `IFToolbarStatusView` tests (9 November 2026).

## Editing

- **Find All in Files waits for a search already running.** A Find in Files search runs on another thread, holding `IFFindInFiles`' lock on its list of things to search, and starting one takes that lock on the main thread. So clicking Find All while a search runs stops the app until that search ends (a search of the documentation took about 3 seconds in the tests, in a Debug build). Then the first search's last progress report, queued meanwhile, stops and hides the progress indicator while the new search runs. Found by reading (6 November 2026).
- **The Find panel and Find in Files overwrite each other's find history.** `IFFindController` and `IFFindInFilesController` both keep their history under `IFFindHistory` in the user's defaults, but each reads it only when it's made, keeps its own copy and writes the whole copy back after each search. So a search in one drops whatever the other has added since it was made. Found by reading (9 November 2026).
- **Find in Files keeps a closed project.** The shared `IFFindInFilesController` holds the project and project controller it last searched for strongly, and its window stays open when the project closes. So it keeps them until Find in Files is used from another project, and clicking a result meanwhile asks the closed project's controller to show it. Found by reading (9 November 2026); what that click does isn't known.
- **Opening an installed extension that's already open opens it again.** `IFAppDelegate`'s `openExtension:`, which the File menu's Open Installed Extension items call, makes a new `IFSingleFile` each time and adds it to the document controller, so a second window shows the same file, and edits in one aren't seen in the other. A project opening an extension (`loadInform7ExtensionWithFullFilePath:`) asks `documentForURL:` first. Found by reading (9 November 2026); not checked in the app.
- **Uncommenting two comments leaves brackets.** Uncommenting a selection of two comments with source between them, such as `[a] b [c]`, takes away only the first and last brackets, leaving `a] b [c`. Found with the comment helpers' tests (5 November 2026).
- **A shift with nothing selected selects text.** With the insertion point in a line, Shift Left or Shift Right selects from the start of the line to the insertion point. At the start of a line, Shift Right selects the new tab and the line's first character, and Shift Left, on a line without a tab, its first character, as `IFSourceSharedActions` makes an empty selection one character long so that it shifts a line. So typing straight after a shift replaces what's selected. Mending it means choosing what to leave selected, such as the insertion point where it was in the text. Found with the `IFSourceSharedActions` tests (7 November 2026).
- **A heading numbered in words stops the numbering.** A heading whose number is a word, such as "Chapter Two", has no number as far as numbering is concerned, so a heading typed after it isn't numbered. Found with the `IFNaturalIntel` tests (5 November 2026).
- **Pasted source can lose the start of a comment.** `IFUtility`'s `unescapeString:`, which decodes code pasted from the documentation, runs an escape to the next `=]`, so pasted source with a comment starting `[=`, as in `[=== Notes ===]`, gets a `?` in its place. Inform's documentation only uses `[=0x....=]` escapes. Found with the `IFUtility` tests (5 November 2026).
- **An Inform 6 header opened on its own isn't highlighted.** A `.h` file opened on its own has the document type `public.c-header`, which `IFProjectTypes`' `fileTypeFromString:` takes for an Inform 6 ICL file, so `IFSingleFile` shows it as Latin-1 with no highlighting. Yet `highlighterTypeForFilename:` gives `.h` files Inform 6 highlighting, as in a project. The code pairs the two on purpose, so it may be meant. Found by reading (6 November 2026).
- **The headings browser's "no headings" messages hardly ever show.** `IFHeaderView` shows `NoHeadingsSet`, which says the project has no headings yet, when its root header has no children, and `NoHeadingsVisible`, which says to choose a depth from the menu, when none are shown. But since Inform 1.64.1 (d4dbbf80, 2016) the root header is a Contents header above the story's; before that it was the story's. So a story with no headings but its title shows Contents and the title, with no message, `NoHeadingsSet` only shows before the browser has any headers, and `NoHeadingsVisible` never does, as the least depth in the menu, 1, shows the story's header. Found with the `IFHeaderView` tests (8 November 2026).
- **A source file that starts with a heading can't show its first section alone.** The source page takes a file's first heading for the story's title, as a story's first line is, and showing the title's section shows the whole file. So in a file whose first line is a heading, such as `Volume 1 - Upstairs`, Show Current Section Only, or clicking that heading in the headings page, shows the whole file. Found with the `IFSourcePage` tests (10 November 2026).

## Preferences

- **The new colour theme sheet doesn't suggest a name, and takes an empty one.** New in the Colour preferences sets the sheet's `themeName` to "Custom", but that doesn't fill in its name field (`IFNewThemeWindow`'s `setThemeName(theName:)` would, which the Objective-C pane couldn't call, and the Swift translation still sets the property), so the field is empty the first time, and after that shows the last name typed. The preferences only refuse a name that's in use, so OK with the field empty adds a theme with an empty name. Found while testing `IFColourPreferences` (8 November 2026), from the code and the nib; not checked in the app.
- **"Also clean out index files" does nothing.** The Advanced preferences keep it, but `IFProject` always cleans with `cleanOutUnnecessaryFiles(false)`, both when a project closes and whenever it writes the project, so the Index folder is never emptied, whatever the preference. It has been so since the first version in git. `IFProjectFile`'s `cleanOutUnnecessaryFiles(alsoCleanIndex:)` would empty it if asked. Either the project should pass the preference, or the check box should go. Found while testing `IFAdvancedPreferences` (8 November 2026).
- **Restoring the defaults re-highlights each source view many times.** In a batch, `IFPreferences` keeps a notification for each change, duplicates and all, and when the batch ends, each one writes the preferences, recalculates the styles and posts its notification, and each Editing notification re-highlights every open source view. So Restore in the editing preferences, which sets 22 preferences, can re-highlight each source view up to 22 times, and Restore in the colour preferences up to 8. Choosing a colour theme re-highlights twice, as `setCurrentTheme:` posts after setting `currentThemeName`, which has already posted, and adding or removing a theme writes the preferences and recalculates the styles twice. Found with the `IFPreferences` tests (7 November 2026).

## Documentation

- **Find in Files searches the old documentation.** `IFFindInFiles`' `addDocumentation` searches the pages named `doc…` and `Rdoc…` (558 of them, last changed in August 2023), but since May 2024 (12375aed) the documentation the app shows is the `WI_…` and `RB_…` pages, which the contents page links to and which are numbered differently: 11.3 is now "Dialogue beats and their cues", not "Pattern matching". So documentation results give the old section numbers and open the old pages, and nothing written since is found. To search the new pages, `IFDocParser` would need to recognise their markers, which have spaces inside the comment (`<!-- SEARCH TITLE "…" -->`), and the Recipe Book test would have to change: the new sort keys start `001` for Writing with Inform and `002` for the Recipe Book, where the old ones started `000` and `001`, and `IFFindResult`'s `recipeBookResult` checks for `001`. The new pages have no example markers, and one search title, `"Making the verb "to weigh""`, has quotes inside it. Found while testing `IFDocParser` (6 November 2026).
- **Help > Recipe Book opens the old Recipe Book.** `IFProjectController`'s `docRecipes:` opens `Rdoc1.html`, the old Recipe Book's first page, not the new one's contents page, `RB_index.html`. Found by reading (6 November 2026).

## Skein

- **A "test me" knot's made-up transcript is lost.** A "test me" knot with no blessed transcript is written with one made of its commands' headings, such as `[1] jump`, which the app reads back as none. Found with the `IFSkein` tests (5 November 2026).
- **Knots once couldn't be clicked or dragged** (seen in the app on 5 November 2026, in a build of `phase5/swift-utility-rest`), then could again in the same run. Not reproduced. The branch `debug/skein-clicks` logs the skein's mouse events, tagged "SKEIN", to read with `log show`. An idea, not checked: the knots' tracking areas use `NSTrackingActiveInKeyWindow`, so if the window wasn't key, a knot under the pointer might never be marked as inside, and a click only acts on a knot that is.
- **Clicking a "test me" knot on the selected line clears the selection, though the cursor says it can't be clicked.** `IFSkeinItemView`'s `canClickItem` makes the cursor over such a knot an open hand, as elsewhere in the skein, but `mouseUp:` doesn't ask it, and clears the selection as for any knot on the selected line. Either the cursor or the click is wrong; `canClickItem` would have suited the click that played to a selected knot, which was never built (removed, 10322b23). Found with the `IFSkeinItemView` tests (9 November 2026).
- **A click on a knot leaves the skein view drag-scrolling.** A knot's `mouseDown:` passes the click on to the skein view, which shows a closed hand and starts drag-scrolling, but a click on the lozenge doesn't pass on `mouseUp:`, so the skein view doesn't stop, and the closed hand stays until the cursor is next set: when the mouse leaves the knot, or the knot moves in the new layout. Nothing else uses the drag-scrolling until the next click starts it again. Not checked in the app. Found reading `IFSkeinItemView` (9 November 2026).
- **Editing a knot's command to a sibling's can take the knot being played out of the skein, which stops the app.** Edit Command takes the knot out and adds it back, which merges it into a sibling with the same command, knot by knot down each thread; a knot that matches one already there is dropped. It moves the story to the merged knot if the edited knot itself is being played, but not if a knot after it is: that knot is left out of the skein, and the story's next command stops the app on `IFSkein`'s "Active item has no skein" precondition, as Delete Threads from Here on the start did (fixed, 6a3ab7a7). For example, with threads "look, north" and "wait, north", playing "wait, north", and editing "wait" to "look". Insert Previous Command can do the same, without moving the story even for the chosen knot, when the chosen knot's parent already has a blank knot followed by one with the chosen knot's command. Found reading `IFSkeinView` (9 November 2026); not checked with a test or in the app.
- **Delete Command loses the selection of a knot after it.** When the selected knot is after the deleted one, it's moved up to the deleted knot's parent with the rest of the thread, but the selection goes to that parent if it has only one child, and to nothing otherwise, as if the selected knot had gone. Found reading `IFSkeinView` (9 November 2026); not checked in the app.
- **Play All carries on after the story is stopped.** Stop ends the story but leaves Play All's remaining knots in `IFProjectController`, which plays to the next of them whenever an input source finishes, so the next Test Me, or playing to a knot from the skein, goes on to play the rest of the skein. Replay drops them; Stop and Go don't. Found by reading (9 November 2026); not checked in the app.

## Web pages

- **Each time the welcome window is shown, it adds another advice web view.** `IFWelcomeWindow`'s `showWelcomeWindow` makes a new web view helper and advice web view every time, and adds the web view to the advice area without taking out the one before, so they pile up, hidden under the newest, which is the only one that loads anything. The window is shown at start-up, by Show Launcher, and when the app is asked to open an untitled file, as when its Dock icon is clicked with no windows open. Showing it downloads the news and keeps it in the user's defaults, so it isn't tested. Found by reading (8 November 2026).
- **Switching to the Documentation or Extensions tab adds two entries to the history.** As the page is switched to, it records the page it shows in the history (`didSwitchToPage`), and then reloads it, and the reload is recorded again, as a second entry: the page leaves out only the loads it counts in `inhibitAddToHistory` (a census's reload, a page from the history, the Documentation page's first page, and the Extensions page's failure page), and this reload isn't counted. While the Extensions page shows its failure page, it records and reloads the page that failed instead, in the same way. So Back would have to be pressed twice to leave the tab, the first time showing the same page again. Counting this reload too may not be safe: going back to the tab loads a page from the history straight after it, and if that load overtakes the reload before it starts, the count is left too high, and the next page shown isn't recorded. The pages could remember which navigations not to record (the `WKNavigation` each load gives) rather than count them. Found by reading (8 November 2026), and checked with a probe of `IFDocumentationPage`: switching to the page while visible asked for the history three times, once for the switch and twice for the reload. Not seen in the app.
- **The Index page records in the history while it's hidden.** Its `webView:didStartProvisionalNavigation:` records each page it starts to show, with a switch to the page, unless it's a page from the history, but unlike the Documentation and Extensions pages it doesn't check that it's visible. So the welcome page it's told to show as the pane is set up is recorded, and so is its reload after each translation, whichever tab is showing then. The history's latest entry is then the Index tab, and Back replays the entry before it, which may be the tab that's already showing, so Back has to be pressed twice. Found by reading (8 November 2026), with the tests (`testTheHistoryWhileHidden`). Not seen in the app.
- **After a project's first translation, the Index tab is blank until a cell is clicked.** As the pane is set up, the Index page is told to show its welcome page, but with no index yet it has no cells, so it shows nothing. After a translation it reloads what it shows, which is nothing, and nothing asks for the welcome page. Found by reading (8 November 2026), with the tests (`testSwitchingToThePageBeforeItShowsAnything`). Not seen in the app.
- **On a case-sensitive volume, the Index page can't show its tabs.** It asks for each tab's page by its name in lower case (`rules.html`), but Inform writes them capitalised (`Rules.html`), so they're only found on a volume that ignores case, as macOS's usually do. Found with the tests (8 November 2026). Not checked on a case-sensitive volume.

## Quick Look

- **The plugin would raise when it makes the preferences.** The Quick Look plugin compiles `IFPreferences` and `IFNaturalIntel`, which call the `NSString` category, but not the category itself. `IFNaturalIntel` never runs there, but `IFPreferences` compares theme names with `isEqualToStringCaseInsensitive:` when it makes its styles, which it does when the shared preferences are first used, so the first preview or thumbnail would raise. It has been so since the call was added (7a02e964, May 2022). Compiling the category's Swift file into the plugin would fix it. Found by reading (5 November 2026, and for `IFPreferences` 7 November 2026). InformQL itself may no longer load on macOS 15; replacing it is Phase 6.

## Building

- **Fresh clones of Zoom don't build ZoomServer.** The external-build-tool `Interpreter` target runs before `Builder` is linked, so `build/interp_*.h` are never generated (`'interp_z3.h' file not found`). It works here because old headers sit in the ignored `zoom/build/` (the same code as freshly generated ones, apart from `#line` paths and order), and until it's fixed a fresh clone of Inform hits it too. The fix generates the headers in a ZoomServer Run Script phase that declares Builder as an input: sent as MaddTheSane/zoom#3 (branch `generate-interpreter-headers` in `~/Code/upstream/zoom`), and applied uncommitted to our `zoom/` until it's merged. Found on 3 November 2026.

## Tests

- **A test host that crashes comes back with the user's preferences.** When the test host crashes, Xcode starts it again for the tests that are left, but by then the tests' home folder exists, as the Test action only removes it before the run, so the new host reads the user's real preferences, and could write them. A crash in `IFSkeinItemTests` during the strict concurrency work did this: the tests after it saw the user's external Inform Core folder, and `IFUtilityTests` failed. Nothing was written. Found by the full check (11 November 2026).
