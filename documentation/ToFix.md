# To Fix

Open bugs in the Inform app and in Zoom and CocoaGlk, found during the modernisation (`modernisation_plan.md`). When one is fixed, take it out of here and record the fix in the plan, with the work it was fixed in. Problems that belong in Inform Core itself are in `for_g.txt`, a local, git-ignored list.

Each says how it was found, and none has been seen in the app unless it says so.

## Extension projects

- **The Public Library page and the app disagree about their messages.** `messages_to_objc.js` posts `askInterfaceForLocalVersion`, `askInterfaceForLocalVersionText` and `downloadMultipleExtensions`, which `IFWebViewHelper` doesn't act on, and its `openURL` posts `openFile`, so the helper takes the URL for a file's path. Inform Core's `pl404.html` also uses the first two's return values at once, which WKWebView messages can't give, so this needs an asynchronous design on both sides (see `for_g.txt`). The helper had handlers for the first two under other names, which nothing reached and whose answers were thrown away; they were taken out (a84b8641), and the lookup of an installed extension's version will have to be written for that design. Older than this work; found reading the scripts (November 2026).
- **A download from the Public Library can't be installed once the next one has arrived.** Downloads go one at a time, and each is handed to the project controller as it arrives, which runs inbuild to report on it and keeps it as the one extension whose install the report's button confirms (`IFProjectController.installExtensionURL`, `confirmInbuildAction`). So if a second download arrives before the first's install is confirmed, its report takes the first's place, and the first has to be downloaded again. Older than this work (1ff5bca8, August 2023); found reading the code while removing the temporary copies of installed extensions (14 November 2026). Not seen in the app. Left for now (14 November 2026): downloads are meant to go one at a time, and the maintainer is content with that for now.
- **An example with a heading can't be tested in an extension project.** Inform 10.2 warns about files in a project's bundle that an ordinary project doesn't have, and an extension project always has some: `Source/extension.i7x` beside `story.ni`, and a skein for each example, `SkeinA.skein` and so on, in place of `Skein.skein` (`IFProjectFile`). That would only be a warning, but in Inform 10.2 a warning about a project's files stops ni with "internal error (Parse tree broken)" when the source has a heading, so testing an example whose source has one fails, as example E of Approaches by Emily Short, "Riverside Path", did for the maintainer (14 November 2026). Reproduced with the bundled ni on copies: with the skeins and `extension.i7x` moved out, the example compiles, and an ordinary project with a heading and one extra file fails the same way. Both halves are Inform Core's, and are in `for_g.txt` (items 13 and 14), with the question of what an extension project should look like for 10.2; the app's side is the layout, if Inform Core doesn't come to accept it.

## Documentation

- **Searching the documentation is slow.** Find in Files reads and parses every documentation page for each search, and the pages the app has shown since May 2024 are about 100 MB, five times the old ones. A search of the documentation takes about 15 seconds in the tests, in a Debug build, against 4 with the old pages, and the whole test run went from about 205 seconds to 374. The parsed text could be kept between searches, or made when the app is built. Found while making Find in Files search the new documentation (11 November 2026); not timed in the app. Left for now (14 November 2026): Release builds are faster, and the maintainer hopes to move the pages' CSS into a separate file, which should make it faster still.

## Zoom and CocoaGlk

Found looking for bugs in Zoom and CocoaGlk at `origin/madds` (15 November 2026; see the plan's Phase 4), and to be fixed upstream. None has been seen in the app.

- **Reading a text file is slow, though not wrong.** CocoaGlk buffers a binary file opened only to read, on the interpreter's side, but not a text file, so each `glk_get_char_stream` from a text file takes a round trip to Inform. A Unicode text file is decoded by `GlkUTF8Stream` a byte or two at a time, so each character read from it takes one, by whichever call. This said that read-only binary files were slow, which was wrong (corrected 16 November 2026).
- The static analyser's findings in their own code, which were listed here, were checked by hand. Apart from `glk_style_measure`'s (in the plan), they are false positives, or small leaks in Zoom's `debug.c` and `rc.c`, of debugging information and at start-up.

## Git, CocoaGlk's Glulx interpreter

Found looking for bugs in Git as CocoaGlk pins it, `zoom/depends/CocoaGlk/depends/git/git-1.3.7` (MaddTheSane/Git `mac1.3.7`, 29dac80: Git 1.3.7 with Mac include paths and quietened warnings), on 18 November 2026. Upstream is DavidKinder/Git, whose `master` has 26 commits since. Inform runs Git only when it is chosen as the Glulx interpreter in the Advanced preferences (the default is Glulxe). Each was reproduced with the pinned source built against cheapglk, with Glulxe as the reference; none has been seen in the app. Paths are relative to the Git folder. To be fixed upstream: the first and fifth by moving Git to DavidKinder's `master` (which needs `fatalErrorI`, and `native_random` if `USE_NATIVE_RANDOM` is defined, in CocoaGlk's `git-1.3.7/cocoastart.m`), the rest in DavidKinder/Git, where none is reported.

- **Random numbers are poor.** Git uses Glulxe's old lagged-Fibonacci generator, seeded with the time in seconds (`terp.c:41-66, 192, 1259-1272`). The low k bits of every result depend only on the low k bits of the seed, so `@random N` for a power of 2 has only N possible sequences, and the first `@random 2` after seeding is 0 for every seed. Stories built with Inform 10 throw away a random number of results, up to 98, at the start to soften this (BasicInformKit's `Startup.i6t`), and still get only 191 different sequences of 12 coin tosses over 100,000 seeds, with the first toss 45/55. Stories built with 6M62 throw away a fixed 100, which leaves exactly 2 sequences of coin tosses, and 4 of `random(4)`. Two runs started in the same second also repeat each other. Fixed upstream in Git 1.3.8 (71f94ec, DavidKinder/Git#18): xoshiro128** when seeded, the system's generator when not.
- **A RESTORE that fails can leave the story without its heap, and one that works loses the heap's free space.** `restoreFromFile` calls `heap_clear()` (`savefile.c:60`) before it checks anything, and `heap_clear` shrinks memory back to the heap's start (`heap.c:63-67`). A save from an earlier build of the same project fails the header check, so the story prints "Restore failed." and goes on with its heap gone; the next use of it is fatal ("Out-of-bounds memory access", or "Attempt to free unallocated address from heap."). Inform 10 stories use the heap once their dynamic memory outgrows the built-in Flex heap (`Flex.i6t` `HeapMakeSpace`), and never give those blocks back. Reproduced with an Inform 10.2 story holding a list of 20,000 numbers: save, change the source, rebuild, RESTORE the save, and the next command ends the story under Git, while Glulxe carries on. Also, the heap chunk is applied as it's read (`savefile.c:165-193`), and Git writes it before the memory chunk, so it's applied before the memory size is restored, so the free space at the end of the heap isn't recorded (`heap.c:335`), and the next allocation that doesn't fit grows memory instead. Glulxe clears the heap when it reads the memory chunk, and applies the heap after the last chunk. Fix: do the same.
- **RESTORE reads past the story file when a run of unchanged bytes crosses the end of the story file's memory.** The memory chunk is XOR-ed with the story file below ExtStart and taken as it is above it, but a run that starts below ExtStart is XOR-ed all the way through (`savefile.c:114-129`), reading up to 255 bytes past Git's copy of the story file (AddressSanitizer: `savefile.c:128`). Those bytes, which should be zero, get whatever is there. Needs the heap (or a larger memory size) and a save whose bytes just before and after ExtStart are unchanged and zero. Fix: decide by the address of each byte, as Glulxe does.
- **RESTORE never finishes if a protected range lies beyond the last byte the save changed.** The loops that fill in the rest of memory only advance outside the protected range (`savefile.c:148-157`). Inform 7 doesn't use `@protect`, so only Inform 6 stories can hit it. Fix: advance the index whether or not the byte is protected.
- **Dividing -$80000000 by -1 kills the interpreter on Intel Macs.** `@div` and `@mod` (`terp.c:385-386`) only check for zero; on x86-64 the division traps (SIGFPE; checked under Rosetta), and on Apple silicon it gives -$80000000 and 0. Fixed upstream (5ae06ca, DavidKinder/Git#24) as the fatal error "Divide overflow", as the Glulx spec now says.
- **Some stack and memory checks are missing, so unusual code can write outside Git's buffers.** Found with AddressSanitizer, and none reported upstream. (1) Entering a stack-argument function (I6's `_vararg_count`, which Inform 10's `Glulx_PrintAnything` and its kin are) checks for one free stack word rather than one per argument (`terp.c:339`: `L5` is always 0 there, where `L2`, the argument count, was meant), so a call made when the stack is almost full writes up to an argument count's worth of words past it; Glulxe stops with "Stack overflow". A runaway recursion in a story could end this way. (2) `@stkcopy` (`terp.c:800-807`) doesn't check for free space. (3) `@mzero` and `@mcopy` (`terp.c:1358-1373`) check an address and length whose sum wraps round, so a destination such as $FFFFFF00 writes before Git's memory. (4) Arguments are copied into a fixed `args[64]` (`terp.c:158`) by calls, `@glk` and functions called from strings, so more than 64 arguments overwrite Git's own stack (the process aborts); the Glulx spec has no such limit. Fix: check `L2 + 1` free words; check free space in `@stkcopy`; compare the length with `gEndMem - address`; refuse, or handle, more than 64 arguments.
- **A damaged save file can write outside the stack.** The stack chunk's length isn't checked against the stack size (`savefile.c:94-99`), and a heap chunk shorter than two words makes `qsort` read past its array (`savefile.c:187`). It needs a damaged save of the same story, since another story's fails the header check first. Fix: check both lengths, as Zoom's restore now does.
- Minor: `@stkpeek` with an index equal to the number of values on the stack reads the word below them rather than stopping (`terp.c:791-794`; `>` should be `>=`). `@restart` doesn't reset the I/O system or the string table as Glulxe does (`terp.c:1243-1253`); Inform 7 sets the I/O system first thing, so it can't notice. Every class of Glk object is numbered from 1, so windows, streams and filerefs share numbers, because the first number comes from the generator before it is seeded (`glkop.c:293`, `git.c:19`); upstream has changed this with the generator.
